# V100（Volta / sm_70）支持说明

目的：把当前分支为 **Tesla V100（sm_70）** 所做的改动完整记录下来。主分支仍在演进、性能还有优化空间；
将来任何新分支只要按本文的清单逐项对照，就能在不重新逆向的前提下重新支持 V100。

适用硬件：Volta 架构（sm_70），本机实测为 `Tesla V100-SXM2-16GB`（16 GB，PCIe，`/proc/driver/nvidia/gpus/*/information`）。
软件前提：CUDA 12 的 NVRTC（本机 `/usr/local/cuda-12.6`，`nvcc 12.6.77`）。

一句话概括整套做法：**引擎的 CUDA kernel 全部经 NVRTC 运行时编译（无 C++ 构建步骤），因此支持 V100 的工作
= 一个编译期 feature 开关 + 把 Volta 缺失的 PTX 原语收敛进少数 inline 封装/宏 + 用 wmma 重写 tensor-core GEMM
+ 让 prefill attention 回退到已有的 f32 路径 + 修一处动态共享内存上限的设置方式。**

---

## 1. Volta 缺什么，影响到哪

| Volta（sm_70）缺失的能力 | 原分支里谁依赖它 | 现在的替代 |
| --- | --- | --- |
| `mma.sync.aligned.m16n8k16`（f16→f32 累加） | `gemm_q` 的 warp 内积 | `gemm_q_v`：`wmma` 的 16×16×16 f16 tile |
| `ldmatrix.sync.aligned.m8n8.x4` | `attn_prefill_t` 的 fragment 载入 | 整条 tensor-core prefill attention 换成 `attn_prefill_llama`（f32 逐 query） |
| int8 tensor core（`mma.sync...s32.s8.s8.s32`，k16/k32） | `gemmi_q` / `gemmi_*`、`gemmis_*`、`quant_q8` 的 int8 MMQ 路径 | 全部禁用，量化 GEMM 一律走 f16 的 `gemm_q_v` |
| `cp.async.cg/ca.shared.global` + `commit_group`/`wait_group` | 24 个调用点（prefill GEMM 的 W/X 双缓冲、`attn_decode_gqa` 的 K/V chunk） | 同步的 `uint4`/`uint2` global→shared 拷贝；`commit`/`wait` 变空操作 |
| `__reduce_max_sync` / `__reduce_min_sync`（sm_80+） | `topk_warp` 的 top-k 选择（2 处） | `__shfl_xor_sync` 手做的 5 级 max/min 归约 |
| 动态共享内存：96 KiB 的请求不一定合法 | `attn_prefill_*`、`attn_decode_gqa_*`、`gemvn*` 都请求 96 KiB | 按 `optin − 该 kernel 的 static_shared` 夹到合法上限，且设置失败不报错 |

直接证据（可用 `tools/v100/nr70` 复现，编译方法见第 8 节）：

```
$ ./tools/v100/nr70 tools/v100/mma_test.cu
sm_70 red.cu: FAIL
ptxas application ptx input, line 35; error   : Feature '.m16n8k16' requires .target sm_80 or higher
ptxas application ptx input, line 35; error   : Argument vector size mismatch for instruction 'mma'
```

共享内存规格不硬编码：代码用设备属性查询。按 CUDA 编程指南，Volta 每 block 默认 48 KiB、opt-in 到 96 KiB；
关键点是 **opt-in 上限要减去 kernel 自己的 static shared**，所以固定写 96 KiB 在 sm_70 上会失败。

## 2. 构建开关（`Cargo.toml`）

```toml
cudarc = { version = "0.19", default-features = false, features = ["std", "driver", "nvrtc", "dynamic-loading"] }

# NVRTC 版本与目标架构的编译开关（互斥，只能开一个）：
#   默认 / --features nvrtc_13   CUDA 13 NVRTC，仅 Ampere 及以上（sm_80+，cp.async 与 int8 tensor core）。
#   --no-default-features --features nvrtc_12   CUDA 12 NVRTC，额外支持 Volta/Turing（Tesla V100 的 sm_70）。
[features]
default = ["nvrtc_13"]
nvrtc_13 = ["cudarc/cuda-13010"]
nvrtc_12 = ["cudarc/cuda-12060"]
```

要点：`cudarc` 的 CUDA 版本 feature **不能**再固定在依赖声明里（原来是 `cuda-13010`），必须挪进这两个互斥 feature，
否则两个后端不可能同时构建。V100 构建命令：

```sh
cargo build --release --no-default-features --features nvrtc_12
```

两条路径都要能编译通过，检查用 `tools/v100/check.sh`（先 `cargo check` 默认，再 `cargo check --no-default-features --features nvrtc_12`）。

## 3. NVRTC 需要 CUDA 头文件（wmma 的代价）

默认（`nvrtc_13`）路径的 kernel 全自包含：只用手写 inline asm，不需要任何 CUDA 头，NVRTC 不必有 include 搜索目录。
`nvrtc_12` 用了 `#include <mma.h>`，而 NVRTC 默认没有 include 搜索路径，所以必须显式给 `-I`。

`src/cuda/mod.rs` 的 `nvrtc_includes()`：`STRATA_CUDA_INCLUDE` 环境变量优先，否则扫 `/usr/local/cuda*` 的 `include`，
只收 **确实存在 `mma.h`** 的目录并去重；`nvrtc_13` 返回空列表。`cubin()` 里若 `nvrtc_12` 一个 include 都没找到就提前报错：

```
nvrtc_12 needs the CUDA headers (mma.h) for wmma: set STRATA_CUDA_INCLUDE to the CUDA include directory
```

移植到新分支时，这一段必须整体保留（它是 `nvrtc_12` 唯一的构建期外部依赖）。

## 4. `src/cuda/kernels.cu` 的改动（8 个 `NVRTC_12` 守卫块）

`src/cuda/mod.rs::source()` 在 kernel 源头部注入 `#define NVRTC_12 {}`（值来自 `cfg!(feature = "nvrtc_12") as u8`），
与既有的 `LLAMA_Q8`、`KV_Q8` 并列。当前 8 个守卫块的位置与作用（行号是本分支实测）：

| 行号 | 内容 |
| --- | --- |
| `kernels.cu:9` | `#if NVRTC_12` → `#include <mma.h>` + `using namespace nvcuda;` |
| `kernels.cu:943` | 新增 `template <int T,int SBB,int BM,int BK,bool SM> __device__ __forceinline__ void gemm_q_v(...)`，并在文件里 `#define GEMM_FN gemm_q_v`（否则 `gemm_q`）。`DEF_GEMM` 宏体只把 `gemm_q` 换成 `GEMM_FN`，`QTYPES(DEF_GEMM)` 不用改 |
| `kernels.cu:1097` | `#if !NVRTC_12` 包住 `mma_s8_16816` / `mma_s8_16832` / `mma_s8_*_b` 与 `scale32<T>()`（int8 tensor core 的 asm 与元信息） |
| `kernels.cu:1121` | `cp_async16` / `cp_async8` / `cp_async_commit` / `cp_async_wait<N>` 的 Volta 回退实现 |
| `kernels.cu:1147` | `#if !NVRTC_12` 包住 `gemmi_q` 与 `DEF_GEMMI`/`ITYPES(DEF_GEMMI)`（int8 prefill GEMM 整体不编译） |
| `kernels.cu:2058` | `redux_max_u32` / `redux_min_u32` + `#define REDUX_MAX/REDUX_MIN`（`topk_warp` 里两处调用点改用宏） |
| `kernels.cu:2209` | `#if !NVRTC_12` 包住 `attn_prefill_t`（依赖 `ldmatrix` + `mma.sync m16n8k16`） |
| `kernels.cu:2416` | `#define FA_FAST(HD, ...)`：`nvrtc_12` 指向 `attn_prefill_llama`，否则指向 `attn_prefill_t`；`DEF_FA` 的 else 分支改用 `FA_FAST` |

### 4.1 `gemm_q_v`（wmma 版 prefill GEMM）的设计要点

照抄时最容易踩的坑都在这里：

- **X/W 的 smem 填充完全沿用 `gemm_q`**：`constexpr int P = BK + 8`（half 的 pitch）、`__shared__ __align__(16) u16 xs[XM*P], ws[64*P]`，
  权重解压仍走既有的 `deq8<T>` 与 `QS<T>`（`T==17|18|21|22` 是查表型，先 `QS<T>::load()` 再 `__syncthreads()`），打包成 half 用 `h2pack`。
  **只有 warp 的内积与写回换成 wmma fragment**，所以 tile 结构、`GemmTile` 语义、`act`（0 存 / 1 `silu(y)*v` / 2 累加）都不变。
- `XM = SM ? 32 : BM`；每 warp 的 tile 数 `MT = SM ? 1 : 2`、`NT16 = SM ? 1 : 2`，即 SM 路径覆盖 16×16、非 SM 覆盖 32×32。
  warp 分配：`wm = SM ? 16*(warp&1) : (warp>>1)*32`，`wn = SM ? 16*(warp>>1) : (warp&1)*32`。
- fragment：`matrix_a 16,16,16 half row_major` 从 `xs + (wm+mt*16)*P + kk`、`matrix_b ... col_major` 从 `ws + (wn+nt*16)*P + kk`，
  pitch 都是 `P`；`kk` 步进 16。
- 写回不能用 wmma 的直接散写：先 `wmma::store_matrix_sync(acc_sm[warp], fc[mt][nt], 16, wmma::mem_row_major)` 到每 warp 一块
  `__shared__ float acc_sm[8][256]`，`__syncwarp()` 后再按 `idx = e + lane` 逐元素写 `y` 并套用 `act`。
- 双缓冲语义保持：`ldw(kb+1)` 在 mma 之前发、`stw()` 在 `__syncthreads()` 之后发；`cp.async` 换成同步拷贝后仍然正确，
  **只是不再与计算重叠**（这是 V100 上 prefill 变慢的原因之一）。
- 求和顺序与 `mma.sync` 不同：可接受，因为正常 tensor-core 路径本就是 f16 近似；`--llama-numerics` 的 f32 路径不经过这里。

### 4.2 `cp.async` 回退为什么是安全的

24 个调用点都经过 `cp_async16/8/commit/wait` 这四个封装，**没有一处直接写 asm**，所以换实现不用碰任何调用点：

```cpp
__device__ __forceinline__ void cp_async16(void* dst, const void* src, bool ok) {
    *(uint4*)dst = ok ? *(const uint4*)src : make_uint4(0, 0, 0, 0);
}
__device__ __forceinline__ void cp_async8(void* dst, const void* src, bool ok) {
    *(uint2*)dst = ok ? *(const uint2*)src : make_uint2(0, 0);
}
__device__ __forceinline__ void cp_async_commit() {}
template <int N> __device__ __forceinline__ void cp_async_wait() {}
```

正确性依赖各调用点**已有的** `__syncthreads()`；条件拷贝（`ok=false` 补 0）必须保持，越界行/列靠它。
移植新分支时的检验方法：`grep -n "cp.async" src/cuda/kernels.cu` 应该只命中这 4 个封装的 `#else` 分支。
本分支实测 `cp.async` 共 32 处提及、24 个调用点，全部收敛在封装里。

### 4.3 prefill attention 回退的边界

Volta 上 `ldmatrix` + `mma.sync m16n8k16` 无法等价替换（`wmma` 的 A/B fragment 布局与 attention 的 Q/K/V 分块方式不匹配），
所以直接复用已经存在的 f32 逐 query 路径 `attn_prefill_llama`（原本只给 `--llama-numerics` 用）。
**decode attention 不需要改**：`attn_decode_*` / `attn_decode_gqa_*` 不用 tensor core 与 `ldmatrix`，只受 `cp.async` 回退影响。

### 4.4 顺带修掉的通用 bug（不属于 V100，但 V100 必走这条路）

`attn_prefill_llama` 原先假设 KV cache 是 f16，而 `--kv q8` 时 cache 行是 `HD` 个 int8 + `HD/16` 个 f16 scale，
按 f16 读会算出 NaN/inf。改动后按 `KV_Q8` 决定行跨度与读法：

```cpp
const size_t krow = KV_Q8 ? (size_t)(HD + HD / 16) : (size_t)HD * 2;
auto krd = [&](const char* row, int d) {
#if KV_Q8
    float s = h2f(*(const u16*)(row + HD + 2 * (d / 32)));
    return (float)(signed char)row[d] * s;
#else
    return h2f(((const u16*)row)[d]);
#endif
};
```

Ampere 上这个 bug 只在 `--llama-numerics` 才触发，所以它在主分支上长期没被发现；V100 把它变成必经路径。
移植时务必带上，否则 `--kv q8` + V100 直接出 NaN。

## 5. `src/cuda/mod.rs` 的改动（5 处）

1. **注入宏**：`source()` 的 format 串里加 `#define NVRTC_12 {}`，实参 `cfg!(feature = "nvrtc_12") as u8`（`mod.rs:98` 附近）。
2. **include 选项**：新增 `nvrtc_includes()`（见第 3 节）；`cubin()` 把编译选项从固定两个变成
   `vec![format!("--gpu-architecture={arch}"), "-std=c++17"]` + includes，并在 `nvrtc_12` 且无 include 时 `bail!`。
3. **符号表按 feature 收缩**（`mod.rs:213` 附近）：int8 MMQ kernel 在 `nvrtc_12` 下不请求符号，与 kernel 侧的
   `#if !NVRTC_12` 配对，否则 `load_function` 会因为符号不存在而报错：
   ```rust
   .chain(QTYPES.iter().filter(|&&t| !cfg!(feature = "nvrtc_12") && !Self::float_ty(t)).flat_map(|&t| [kname("gemmi", t), kname("gemmis", t)]))
   ```
   **注意配对关系**：kernel 侧排除哪些 `extern "C"` kernel，这里就必须同样排除，两边不一致会在启动时报
   `kernel <name>: ...`（`load_function` 的 context）。类型集合来自两处宏：`src/cuda/mod.rs:14` 的
   `const QTYPES: [GgmlType; 22]`（全部量化类型）与 `kernels.cu:706` 的 `ITYPES(...)`（有 int8 kernel 的那些：
   `q8_0 q2_k q3_k q4_k q5_k q6_k` 加 IQ 系列）。`QTYPES` 定义 `FTYPES(X) ITYPES(X)`（`kernels.cu:709`），
   所以 f16 类（F32/F16/BF16）本来就不在 int8 链里，`!Self::float_ty(t)` 与 `ITYPES` 是同一件事的两侧。
4. **动态共享内存上限**（`mod.rs:225` 附近）。原来是固定 `set_attribute(..., 96 << 10)?`：
   ```rust
   let optin = ctx.attribute(sys::CUdevice_attribute::CU_DEVICE_ATTRIBUTE_MAX_SHARED_MEMORY_PER_BLOCK_OPTIN).unwrap_or(96 << 10) as usize;
   let static_sm = f.get_attribute(sys::CUfunction_attribute::CU_FUNC_ATTRIBUTE_SHARED_SIZE_BYTES).unwrap_or(0) as usize;
   let max_dyn = (96usize << 10).min(optin.saturating_sub(static_sm));
   let _ = f.set_attribute(sys::CUfunction_attribute::CU_FUNC_ATTRIBUTE_MAX_DYNAMIC_SHARED_SIZE_BYTES, max_dyn as i32);
   ```
   两处要点：(a) 必须减 `static_shared`；(b) 用 `let _ =` 吞掉失败——这个属性只是**上限声明**，真正的用量由 launch 传，
   设不上不代表 kernel 不可用。适用对象是 `attn_prefill*`、`attn_decode_gqa*`、`gemvn*`。
5. **`mmq()` 短路**（`mod.rs:291` 附近）：`if cfg!(feature = "nvrtc_12") { return false; }`，
   让所有量化类型的 prefill GEMM 都走 f16 路径，不去调 `quant_q8` + int8 MMQ。这是行为开关，必须与第 3 点的符号排除同时存在。

另外顺手加了 `.context("CUDA init: new_stream")` / `.context("CUDA init: compute_capability")`，
以及 NVRTC 库缺失的错误消息按 feature 显示 `the CUDA 12 / CUDA 13 NVRTC library (libnvrtc.so) is not installed`
——这两个分支都是 `cfg!` 常量条件，**构建时会被常量折叠**，所以可以用 `strings target/release/strata | grep -oE "CUDA 1[23]"`
反查某个二进制到底是哪个 feature 编的（只出现一个 = 另一个分支被折叠掉了）。本分支的
`target/release/strata`（Nov 10 21:59 构建）里只有 `CUDA 12`，即它是 `nvrtc_12` 构建。

## 6. `README.md` 的说明（面向用户，保持原文口径）

Build 段已改为：默认目标 Ampere+（sm_80，`cp.async` 与 int8 tensor core）；要跑 Tesla V100（Volta sm_70，缺
`cp.async` 与 int8 tensor core）用 `cargo build --no-default-features --features nvrtc_12`，它走 CUDA 12 NVRTC，
sm_70 kernel 经 wmma（Volta 的 16×16×16 f16 tensor core）编译、用同步 global→shared 拷贝替代 `cp.async`，
所有量化矩阵乘走 f16 路径、prefill attention 回退 f32 kernel。新分支若改了这些行为，请同步改 README。

## 7. 移植到新分支的 checklist

按顺序做，每步都有可验证的检查：

1. `grep -nE "mma\.sync|ldmatrix|cp\.async|__reduce_(max|min)_sync|wgmma|redux" src/cuda/kernels.cu`
   —— 列出主分支新引入的 Volta 缺失原语。若出现了新的内联 asm（不在封装里），把它收进封装再加回退，别在调用点写 `#if`。
2. `Cargo.toml`：把 `cudarc` 的版本 feature 挪进互斥的 `nvrtc_13` / `nvrtc_12`。
3. `mod.rs::source()` 注入 `NVRTC_12` 宏；加 `nvrtc_includes()` 与 `cubin()` 的 include/bail。
4. `kernels.cu`：`#include <mma.h>` 守卫 → 加 `gemm_q_v` + `GEMM_FN` → `cp_async*` 回退 → `REDUX_*` 宏 →
   `#if !NVRTC_12` 包住 int8 的 mma asm / `gemmi_q` / `DEF_GEMMI` 与 `attn_prefill_t` → `FA_FAST`。
5. `mod.rs`：符号表排除 `gemmi`/`gemmis`；`mmq()` 返回 false；shared 上限改成 `min(96 KiB, optin − static_shared)` 且吞失败。
6. 确认 `attn_prefill_llama` 能读 q8 KV（第 4.4 节），以及 decode attention 不含 `ldmatrix`/`mma.sync`。
7. 两种 feature 都 `cargo check` + `cargo build --release`（`tools/v100/check.sh`）。
8. 单独编译两份 kernel 源做对照（`tools/v100/mk.sh` 与 `check.sh` 都自带 `cd`，从任何目录跑都行；产物落在 `tools/v100/`
   并已 gitignore）：`mk.sh` 生成 `full70.cu`（`NVRTC_12 1`）与 `full80.cu`（`NVRTC_12 0`），两份只差宏那一行；再用
   `tools/v100/nr70` 直编并拿到 ptxas 的原始报错，最快定位"哪个 kernel 在 sm_70 编不过"：
   ```sh
   bash tools/v100/mk.sh
   g++ -O0 tools/v100/nr70.cpp -I/usr/local/cuda-12.6/include -L/usr/local/cuda-12.6/lib64 -lnvrtc -o tools/v100/nr70
   INC=/usr/local/cuda-12.6/include                    # 有 mma.h 的那个目录
   ./tools/v100/nr70 tools/v100/full70.cu -I$INC       # Volta 路径，期望 OK
   ./tools/v100/nr70 tools/v100/full80.cu --gpu-architecture=sm_80 -I$INC   # Ampere 路径未被破坏，期望 OK
   ./tools/v100/nr70 tools/v100/full70.cu              # 不给 include：期望 FAIL（mma.h），即第 3 节的存在理由
   ```
   `mk.sh` 的早期版本用 `../src/...` 相对路径且不会 `cd`，从仓库根跑会静默拼出只有 507 字节头部的残缺文件并在仓库根
   留下 `full70.cu`/`full80.cu`——现在已修，移植时别把那个坑带回脚本。
9. 上真机跑：`strata info --model <file>` → `strata generate --gpu` → `strata bench --gpu`。
   首次运行会打印 `compiling CUDA kernels for sm_70 (first run only, ~15 s)` 并写 cubin 缓存
   （`$XDG_CACHE_HOME/rusting_strata/<16hex>.cubin`，默认 `~/.cache/rusting_strata/`；hash 受 `--kv q8` 与
   `--llama-numerics` 影响，所以会看到多个 cubin 文件）。每次改 kernel 都会留下 stale cubin，由 `prune_ptx` 按 7 天清理。
   跑完用 `cuobjdump --dump-resource-usage ~/.cache/rusting_strata/<hash>.cubin` 验收：`gemmi*` 应为 **0 个**、
   `attn_prefill*` 只应有 f32 版那三个——这就是第 5 节"两侧排除必须配对"的客观检验，比读代码可靠。
10. 数值验证：与 `--llama-numerics`/CPU 路径对照 `strata score` 或 `tools/parity.py`；V100 的 f32 prefill attention 与
    `--llama-numerics` 是同一条路径，所以两边应完全一致，这是最干净的自检。

## 9. 当前验证状态与已知限制

诚实记录，别把没测过的当结论：

**已实测（本轮）**：

- `bash tools/v100/check.sh`：两种 feature 的 `cargo check` 都通过（`default_exit=0`、`nvrtc12_exit=0`）。
- `bash tools/v100/mk.sh` 生成当前 kernel 源后，用 `tools/v100/nr70` 直编（无需 GPU）：
  - `./nr70 full70.cu -I/usr/local/cuda-12.6/include` → **OK**，cubin 6,285,440 字节；
  - `./nr70 full80.cu --gpu-architecture=sm_80 -I/usr/local/cuda-12.6/include` → **OK**，cubin 7,035,840 字节
    （Ampere 路径没被破坏）；
  - `./nr70 full70.cu`（不给 include）→ **FAIL**：`catastrophic error: could not open source file "mma.h" (no directories
    in search list)`。这就是第 3 节 include 逻辑的存在理由，也说明新分支若丢了 `nvrtc_includes()` 会在此处立刻暴露。
- 引擎产物侧的证据（`~/.cache/rusting_strata/`，三个 cubin 最新 Nov 10 23:46）：
  `cuobjdump --list-elf` 显示三个**都是 sm_70**；`cuobjdump --dump-resource-usage` 数出 242 个函数，其中
  `gemmi*` **0 个**（int8 prefill GEMM 确实没编进产物）、`attn_prefill*` 只有 `attn_prefill_64/128/256`
  （静态 SHARED 0，即 tensor-core 版 `attn_prefill_t` 已被排除、只剩 f32 回退）、
  `attn_decode_gqa_128` 是 `REG:120 SHARED:2112`（静态 2112 字节，正是第 5 节 `optin − static_shared` 要减的那部分）。
  符号清单可用 `cuobjdump --dump-resource-usage <cubin> | grep -oE "Function [a-z0-9_]+"` 提取（本分支存为 `tmp/cubin_syms.txt`，属临时产物、不入库）。

**未实测**（要在能访问 GPU 的环境补）：

- **本会话的容器无法访问 GPU**：`nvidia-smi` 报 `Failed to initialize NVML: Insufficient Permissions`，
  `tools/v100/attr` 全部返回 `rc=3`（`cuInit` 失败）。所以 Volta 的 `MAX_SHARED_MEMORY_PER_BLOCK` / `..._OPTIN` 具体数值没有实测，
  本文只给代码逻辑与 CUDA 指南规格；`tools/v100/attr` 的逐档 `set` 实验要重跑。
- 端到端运行时验证（`--gpu` 下 info/generate/bench）与数值 parity 都还没跑；判定"当前 release 是 `nvrtc_12` 构建"
  的依据是字符串常量折叠（第 5 节）加上面的 cubin 证据，不是引擎运行结果。
- `~/.cache/rusting_strata/strata-Qwen3.8-Flash-Next-GSQ-RCO-IQ2_XS-00001-of-00002.json` 里的
  `prefill_tok_s 248.0 / decode_tok_s 17.0 / chunk 4096 / mtp 0` 属于哪台机器未确认。若确为 V100，
  这个 prefill 数字就是 f32 attention 回退的代价。
- 已知性能代价（按机制，非实测）：prefill attention 走 f32 逐 query（最慢的一条）；`cp.async` 同步化丢掉访存与计算的重叠；
  所有量化矩阵乘失去 int8 tensor core 增益，改走 f16 wmma；wmma 的 16×16 tile 粒度比 `mma.sync` 的 16×8 粗。
- 后续可优化方向：(1) 用 wmma 重写 prefill attention（绕开 `ldmatrix`：手工把 Q/K/V 排成 wmma 的 A/B fragment 布局）；
  (2) 为 sm_70 单独调 `GEMM_BM`/`GEMM_BK`（现在默认 128/64，由 `tools/v100/gemm_bench.cu` 这类工具扫）；
  (3) 把 Volta 的同步 smem 拷贝改成"先算后拷"的手工双缓冲以找回一部分重叠；
  (4) 若 `attn_decode_gqa_*` 在 sm_70 上撞到 smem 上限，考虑减少 K/V chunk 数而不是继续抬 opt-in。

## 10. 一句话原则

**Volta 支持的正确维护方式不是到处加 `#if`，而是让"缺失原语"只存在于 4 个 `cp_async*` 封装、
`REDUX_MAX/MIN` 宏、`GEMM_FN` 宏、`FA_FAST` 宏和 2 个 `#if !NVRTC_12` 大块里。**
主分支每次改动后，用第 7 节第 1 步的 grep 检查有没有新原语绕过封装——这是整套改动能否被"重新应用"的关键。
